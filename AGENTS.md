# FinZvit Development & Engineering Protocol

> **Обов'язкові правила для штучного інтелекту, субагентів та розробників у проєкті FinZvit.**
> Ці правила мають найвищий пріоритет і повинні безумовно виконуватись під час кожної зміни.

## 1. 🗄️ Дисципліна міграцій бази даних (Суворе правило імутабельності)

1. **ЗАБОРОНЕНО редагувати старі файли міграцій**:
   * Будь-який файл у папці `supabase/migrations/*.sql`, що був створений або застосований раніше, є **незмінним (immutable)**.
   * Ніколи не виправляйте помилки чи не вносьте зміни у старі міграції заднім числом!
2. **ЗАВЖДИ створюйте новий файл міграції**:
   * Для будь-якої зміни схеми, створення індексу чи оновлення SQL-функції генеруйте новий файл:
     ```bash
     bash scripts/new-migration.sh <назва_міграції>
     ```
   * Або вручну створюйте наступний за порядком файл: `supabase/migrations/YYYYMMDD00000X_<назва>.sql`.
3. **Безпечне оновлення функцій (PostgreSQL)**:
   * Якщо у функції змінюється список або типи вихідних колонок (`RETURNS TABLE`), перед `CREATE OR REPLACE FUNCTION` обов'язково викликати:
     `DROP FUNCTION IF EXISTS public.<назва_функції>(<типи_параметрів>);`
4. **Синхронізація документації**:
   * Після створення нової міграції оновіть консолідований файл загальної схеми: [`docs/SUPABASE_SCHEMA.sql`](file:///Users/denys/dev/experiments/finzvit/docs/SUPABASE_SCHEMA.sql).

## 2. 🛡️ Верифікація та прогін тестів перед комітом (Zero-Defect Policy)

Перед кожним комітом або звітом користувачу про завершення завдання **ОБОВ'ЯЗКОВО** запустити тестовий скрипт:
```bash
./scripts/qa.sh
```

Цей скрипт автоматично перевіряє:
1. **Security & Secret Leak Audit**: автоматичне сканування на витік секретів, API-токенів, приватних ключів та конфігураційних файлів (`scripts/security_check.py`).
2. **Python Unit Tests**: всі 67 тестів (парсери XML, обробка edge-cases, розрахунки фінпоказників).
3. **Web Build (Astro + Vite + TypeScript)**: повна компіляція фронтенду, типізація та генерація статичних маршрутів без жодної помилки.

> ⚠️ **Якщо хоча б одна перевірка падає — створення коміту ЗАБОРОНЕНО.** Спочатку виправляється помилка, після чого скрипт запускається повторно.

## 3. 📝 Правила комітів (Conventional Commits)

Всі коміти повинні суворо слідувати стандарту Conventional Commits:
* `feat:` — нова функціональність або компонент (напр. `feat(kpi): add cash flow coverage ratio`)
* `fix:` — виправлення багу чи помилки (напр. `fix(search): fix 304 asset fallback in worker`)
* `perf:` — оптимізація швидкодії чи пам'яті (напр. `perf(db): optimize trgm search query`)
* `refactor:` — зміна коду без зміни функціоналу
* `test:` — додавання або виправлення тестів
* `docs:` — оновлення документації
* `chore:` — рутинні завдання, оновлення конфігурацій

Повідомлення коміту має бути інформативним, із чітким описом причин зміни та наслідків.

## 5. ⚡ 100% Статичний фронтенд, Cloudflare Worker та багаторівневе кешування

1. **Принцип 100% статичного сайту (Zero-SSR Jamstack Architecture)**:
   * Сайт побудовано виключно у режимі Static Site Generation (`output: 'static'` в `astro.config.mjs`). Жодного сервера рендерингу (SSR) на бекенді!
   * Усі загальні сторінки (`/`, `/404`, а також універсальна HTML-оболонка `/company/`) компілюються під час збірки в статичні файли в `web/dist/`.
   * Головна сторінка `/`, сторінка `404` та всі статичні ресурси (`/_astro/*`, іконки, CSS) обслуговуються безпосередньо Cloudflare Assets CDN і **категорично не повинні виконувати код воркера** (відповідно до налаштування `run_worker_first: ["/data/*", "/company/*"]` у `wrangler.jsonc`).

2. **Суто клієнтський пошук напряму в Supabase (Direct Client-to-Supabase Search)**:
   * Пошук компаній виконується **виключно на клієнті в браузері** через `@supabase/supabase-js`.
   * Запити йдуть **напряму на хост Supabase** (`https://<project>.supabase.co/rest/v1/rpc/search_companies`), **повз Cloudflare Worker**.
   * **Категорично заборонено** проксувати пошукові запити через Cloudflare Worker! Прямий запит заощаджує 100% безкоштовного ліміту у 100 000 викликів воркера/день і зменшує мережеву затримку до 15-25 мс.
   * Обов'язковий debounce (мінімум 180 мс) та мінімальна довжина запиту від 2 символів у `SearchBar.tsx` для захисту бази від спаму.

3. **Багаторівневе кешування даних («Воркер R2 спрацьовує лише раз»)**:
   * Для фінансових звітів (`/data/{year}/{edrpou}.json`) діє суворе 4-рівневе кешування:
     1. **Кеш браузера (Browser Disk Cache)**: `Cache-Control: public, max-age=31536000, immutable`. Повторний візит користувача бере файл з локального диска ПК (0 мс, 0 мережевих запитів).
     2. **Cloudflare Edge CDN Cache**: `s-maxage=31536000` та `Cache-Tag`. Запити від інших клієнтів обслуговуються з найближчого Edge POP без запуску воркера.
     3. **In-Memory LRU кеш воркера**: пам'ять ізоляту зберігає до 500 гарячих звітів. Відповідь віддається за < 1 мс без звернення до R2.
     4. **Cloudflare Cache API (`caches.default`)**: системне кешування у воркері для кастомних доменів.
     5. **Сховище Cloudflare R2**: викликається **рівно 1 раз** при найпершому «холодному» запиті до даного ЄДРПОУ.

4. **Протокол інвалідації та очищення кешу при оновленні файлів у R2**:
   Коли звіт компанії або річний датасет оновлюється/перезавантажується в R2, діють наступні правила інвалідації:
   * **Глобальне скидання (Global Cache Invalidation)**:
     Збільшити версію `CACHE_VERSION` у `web/wrangler.jsonc` (наприклад, `v3` ➔ `v4`) та `web/src/lib/api.ts`. При наступному запиті воркер автоматично очищує свій `memoryCache` та `caches.default`, а браузери клієнтів звертаються за новою адресою `/{year}/{edrpou}.json?v=v4`, гарантуючи оновлення даних для всіх користувачів світу.
   * **Точкове скидання за тегами (Cache-Tag Purging)**:
     Кожен файл компанії віддається з унікальним тегом: `Cache-Tag: company-{edrpou},year-{year},finzvit-data`. Для скидання кешу конкретної компанії викликається Cloudflare Purge API за тегом `company-{edrpou}`.
   * **Ручне очищення зони (Cloudflare Dashboard / CLI)**:
     У панелі Cloudflare: **Caching** ➔ **Configuration** ➔ **Purge Cache** (Custom Purge за URL або Purge Everything).

5. **Статичні ассети у воркері**:
   * При перехопленні `env.ASSETS.fetch(request)` обов'язково перевіряти `if (assetRes.status < 400)`, щоб не ламати умовні запити клієнтів з `If-None-Match` (HTTP `304 Not Modified`).

## 6. 💎 Оптимізація під безкоштовні ліміти (Free Tier Optimization Principle)

Будь-які зміни в архітектурі, коді воркера чи фронтенду **зобов'язані** проектуватись із суворим дотриманням лімітів безкоштовних тарифів:

1. **Supabase Free Tier (Ліміт диску 500 МБ, ліміт з'єднань)**:
   * У таблиці `companies` зберігаються **виключно мінімальні дані для автокомпліту**: `edrpou`, `name`, `kved`, `year`, `weight`.
   * **Категорично заборонено** зберігати в Postgres повні JSON-звіти, рядки балансу, лог-таблиці переглядів або важкі текстові реквізити (адреси, ОПФ тощо). Завдяки цьому вся база України (435 000+ підприємств) займає лише **~40 МБ** диску (із запасом у 12 разів до ліміту 500 МБ).
   * Пошук реалізовано виключно через RPC `search_companies` з `pg_trgm` GIN індексами для миттєвої відповіді (< 15 мс) без навантаження на CPU бази.

2. **Cloudflare R2 Free Tier (10 ГБ сховища, 1 млн Class A операцій/міс, 10 млн Class B/міс)**:
   * **Gzip Pre-compression**: Всі JSON файли (`/{year}/{edrpou}.json`) зберігаються в R2 вже стисненими gzip (`Content-Encoding: gzip`). Повний річний архів України стискається з ~5 ГБ до **~800 МБ** (вміщує 10+ років звітів у безкоштовні 10 ГБ).
   * **1 компанія = 1 файл (Consolidated File)**: Всі форми компанії (Ф1-Ф5, примітки, KPI) об'єднуються в один файл. Це скорочує кількість операцій запису (Class A PUT) з ~2.5 млн до 435 тис. за річний датасет і потребує лише 1 операцію читання (Class B GET) при перегляді сторінки компанії.
   * **Жодних дублюючих реєстрів у R2**: Заборонено заливати в R2 гігантські плоскі реєстри (на зразок `companies_registry.json`). Пошук виконує виключно Supabase.

3. **Cloudflare Workers Free Tier (100 000 запитів/день, 10 мс CPU)**:
   * **Zero-CPU Streaming**: Якщо клієнт підтримує gzip (`Accept-Encoding: gzip`), воркер напряму стрімить стиснений байтовий потік з R2 з `Content-Encoding: gzip` без витрат процесорного часу на декомпресію.
   * **Edge Caching**: Всі запити до R2 мають заголовки `Cache-Control: public, max-age=31536000, immutable` та `Cache-Tag`, що дозволяє Cloudflare CDN кешувати звіти на Edge-рівні, мінімізуючи виклики до воркера та R2.
   * **Універсальний HTML Shell**: Замість SSR генерації для 435 тис. компаній воркер віддає один статичний HTML-шаблон для клієнтської гідрації даних з CDN.
   * **Суто статичні ассети**: Запити до головної сторінки та статичних файлів не чіпають воркер і не витрачають добову квоту запитів.

4. **GitHub Free Tier (Розмір сховища репозиторію, ліміти GitHub Actions)**:
   * **Жодних великих бінарних файлів чи архівів у Git**: вхідні ZIP-архіви датасетів (гігабайти) та вихідні JSON дампи повинні бути виключно в `.gitignore`.
   * **Швидкі та ізольовані тести**: юніт-тести та QA-перевірка (`./scripts/qa.sh`) повинні виконуватися за лічені секунди без зовнішніх мережевих залежностей.

## 7. 🔒 Безпека та захист від витоку секретів (Zero-Secret & Zero-Token Leak Policy)

Репозиторій проєкту FinZvit є **публічним на GitHub**. Будь-які секретні дані, токени доступу, паролі, реальні ID проєктів або навіть клієнтські ключі **категорично заборонено** хардкодити чи комітити у відкритому вигляді в репозиторії Git:

1. **Сувора заборона коміту будь-яких токенів та ідентифікаторів проєкту**:
   * **Ніколи не хардкодити та не комітити**:
     * Токени Cloudflare API, R2 Access/Secret Keys.
     * Supabase Service Role або Publishable / Anon ключі (`sb_publishable_*`, `sbp_*`, `eyJ*`).
     * Реальні URL проєкту Supabase (`https://<project-ref>.supabase.co`).
     * Google Analytics Measurement IDs (`G-*`).
     * Паролі баз даних, приватні ключі SSL/SSH (`*.pem`, `*.key`, `*.pfx`, `id_rsa`).
   * **Категорична заборона «дефолтних фолбеків» (No Hardcoded Fallbacks)**:
     * Ніколи не прописувати реальні ключі, URL або GA ID у виразах на зразок `import.meta.env.KEY || 'реальний_ключ'`!
     * Дозволено лише безпечний порожній фолбек: `import.meta.env.PUBLIC_KEY || ''`.
2. **Архітектура інжектування змінних без хардкоду**:
   * **Локальна розробка**: змінні конфігуруються виключно у файлі `web/.env.local` (який суворо заігнорений у `.gitignore`). У репозиторії зберігається лише шаблон `.env.example` із безпечними плейсхолдерами (`your-project`, `sb_publishable_your_key_here`, `G-XXXXXXXXXX`).
   * **Продакшен-збірка у Cloudflare Workers**:
     * Оскільки фронтенд є 100% статичним (Astro SSG), змінні для клієнта (`PUBLIC_*`) повинні бути присутні під час команди `astro build`.
     * У Cloudflare Dashboard вони налаштовуються у розділі **Settings ➔ Build ➔ Build Variables and Secrets** (Build-time змінні).
     * Для сумісності з `wrangler` у `web/wrangler.jsonc` обов'язково встановлено `"keep_vars": true`, щоб Wrangler не намагався видалити змінні з Dashboard або синхронізувати їх у git.
3. **Автоматизований захист перед кожним комітом**:
   * Перед кожним комітом скрипт `./scripts/qa.sh` та локальний Git hook (`.git/hooks/pre-commit`) автоматично сканують робоче дерево та staged-файли за допомогою `scripts/security_check.py`.
   * Сканер блокує не лише приватні ключі та паролі, а й Supabase Publishable ключі, URL проєктів та GA ідентифікатори.
   * Якщо виявлено хоча б один токен, незаігнорений `.env` або реальний ID — створення коміту **миттєво блокується з кодом 1**.
4. **Дії у разі випадкового витоку**:
   * Якщо секрет випадково потрапив у робоче дерево — негайно скинути зміни (`git restore`) та перевірити `.gitignore`.
   * Якщо секрет коли-небудь потрапив у відправлений коміт — **негайно відкликати (ротувати) скомпрометований токен** у відповідному сервісі (Cloudflare / Supabase), оскільки видалення коміту в Git не гарантує конфіденційності, якщо історію вже було клоновано.

## 8. 🚫 Сувора заборона Git Push для штучного інтелекту (No AI Push Policy)

1. **ЗАБОРОНЕНО викликати `git push`**:
   * Штучний інтелект, агенти та субагенти **категорично не мають права викликати команду `git push`** у віддалений репозиторій.
   * Усі пуші (`git push origin main` тощо) виконує **виключно користувач-людина** самостійно.
2. **Обов'язковий протокол завершення завдання для ШІ**:
   * **Підготовка коду**: внести необхідні зміни, виконати оптимізацію та рефакторинг.
   * **Повна перевірка**: запустити `./scripts/qa.sh` (сканування секретів, 67 тестів, компіляція фронтенду).
   * **Синхронізація документації**: оновити стан задач (`docs/TASKS.md`), схему бази (`docs/SUPABASE_SCHEMA.sql`), архітектуру (`docs/ARCHITECTURE.md`).
   * **Створення локального коміту**: зафіксувати зміни локально згідно з правилами Conventional Commits.
   * **Фінальний звіт**: проінформувати користувача про виконану роботу, статус перевірок і готовність до відправки (користувач пушить власноруч).
